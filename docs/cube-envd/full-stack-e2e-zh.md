## 1. 结论速览

| 维度 | 结果 |
|---|---|
| **进程/PTY 大突发输出** | 🟥 **cube-envd 在约 2 MiB 后主动掐断流**（`resource_exhausted`、无 EndEvent），Go 用背压、一字节不丢。**详见 [output-stream-truncation-zh.md](./output-stream-truncation-zh.md)** |
| 逐 token 流式 / 按键回显 / 命令时延 | ✅ 两侧一致（毫秒级），不是差异来源 |
| 官方 SDK 兼容套件（288 用例） | **逐一相同**：271 passed / 17 skipped（含 1 xfail），stock 与 cube-envd 无一处状态不同 |
| 新能力：终止原因 | cube-envd **有**（`signal` / `oom_killed` / `killed_by`），镜像自带 Go envd **全为 null** |
| 新能力：每命令 cgroup | cube-envd 每个命令独立 cgroup（`.../user/process-2-10/`），Go envd 没有 |
| PTY 会话建立+销毁 | 中位数 4.6 ms（Go）→ 3.0 ms（cube-envd），约 1.5× |
| 下载吞吐（64 MiB，同机同代理） | 1375 MiB/s（Go）→ 475 MiB/s（cube-envd），**2.9× 慢** |
| 下载 gzip | 机制不同：Go 由 envd 自己压缩；我们不压，只有 CubeProxy 对文本类型压（level 1） |
| `POST /files/compose` | Go 200 / 我们 501（协议缺口，但**两套 SDK 都不调用**） |
| `HEAD /files` | Go 405 / 我们 200 |
| Range / 416 / 404 / 400 | 完全一致 |
| 上传吞吐 | 混合：octet-stream 我们慢 1.37×，multipart 我们快 1.29× → 无稳定差异 |

### 2.1 三个踩过的坑（都会让部署直接失败）

1. **从国内拉 GitHub 只有 ~10 KB/s**。575 MiB 的 PVM 内核 RPM 在服务器上下载要
   约 15 小时。改为本地下载（11–13 MB/s）再 `rsync` 推上去（3.97 MB/s，约 2.5 分钟）。
   `raw.githubusercontent.com` 在服务器上直接超时，`host_grub_config.sh` 同样走推送。
   安装器本身走 `MIRROR=cn`（`cnb.cool`，实测 8–10 MB/s）没有问题。
2. **PVM 启动参数必须走 BLS**。OpenCloudOS 用 `/boot/loader/entries/*.conf`，
   `grub2-mkconfig` 不会重写这些条目，所以厂商脚本改 `GRUB_CMDLINE_LINUX` 之后
   重启，`/proc/cmdline` 里**没有** `clearcpuid=...`/`clocksource=tsc` 等参数。
   正确做法是 `grubby --update-kernel=<vmlinuz> --args="..."`。
   （顺带：该脚本按 key 去重，会把 `console=ttyS0,115200` 挤掉，需要补回。）
3. **`kvm_pvm` 不会自动加载**。首次启动后 `lsmod` 为空、`/dev/kvm` 不存在，
   手动 `modprobe` 才有。需要写 `/etc/modules-load.d/kvm-pvm.conf`。
   另外厂商脚本会开 `module.sig_enforce=1`，上机前先实测该模块在强制签名下能加载
   （`modinfo` 显示由 `Build time autogenerated kernel key` 签名，实测
   `modprobe -r` 后重载成功）。

## 3. 怎么保证这组 A/B 是可信的

同一个镜像、同一套组件、同一台机器、同一个客户端，只换 envd 二进制：

| | 模板 | 实际服务的 envd | 版本 / commit | 二进制 sha256 | 进程 |
|---|---|---|---|---|---|
| stock | `tpl-d4d23eaf66c24c218caa0b4f` | 镜像自带 `/usr/bin/envd`（Go） | `0.5.11` / `b781ad4` | `4c712122…` | `/proc/3/exe` |
| pr27 | `tpl-79b19801602340e08d481c8d` | 注入的 `/usr/local/bin/envd`（Rust） | `0.1.0` / `c1cd0a0d` | `2912f8a2…` | `/proc/2/exe` |

构建命令（pr27 侧）：

```bash
cubemastercli tpl create-from-image \
  --image cube-sandbox-cn.tencentcloudcr.com/cube-sandbox/sandbox-code:latest \
  --writable-layer-size 1G --expose-port 49999 --expose-port 49983 \
  --probe 49999 --probe-path /health \
  --enable-inject-envd --envd-path /root/cube-envd-pr27 \
  --env ENVD_BIN=/usr/local/bin/envd
```

两点容易被忽略、但不处理就会毁掉对照实验的地方：

* 注入写的是 `/usr/local/bin/envd`，而镜像 entrypoint 跑的是 `/usr/bin/envd`，
  **两个 envd 会抢 49983**。加 `--env ENVD_BIN=/usr/local/bin/envd` 让两侧都指向
  我们的二进制，这样无论谁抢到端口，提供服务的都是被测版本，不存在竞态。
* 上机后用 `/proc/<pid>/exe` + sha256 复核"到底是谁在服务"，而不是相信配置。

> 一个观察：镜像自带的是 Go envd **0.5.11**（不是我们对照的 0.5.13），
> 所以这组对照就是"用户实际拿到的那个镜像"的真实行为。

## 4. 结果一：官方 SDK 兼容套件

`tests/e2e/sdk_compat`（288 用例，`--run-e2e`），客户端用**本分支的 Python SDK**
（即包含终止原因改动的那版，`CUBE_PYTHON_SDK_PATH` 指向分支源码），两个模板各跑一遍。

### 4.1 先跑的一次是 4 worker 并行，出现 1 例失败

pr27 侧 `1 failed, 270 passed`，stock 侧 `271 passed`。唯一差异：

```
cases/templates/test_alias.py::test_template_create_from_image_and_cleanup
Failed: template tpl-ee2ef9382f104752ab2443e9 did not reach READY within 480s
```

我一开始把这说成"节点抖动"，这是**不成立的**——机器只有我在跑。查下去的实际原因：

* 这条用例执行 `Template.build(image=...)`，自己**从镜像新建一个模板**，
  和 `CUBE_TEMPLATE_ID`、和 cube-envd **完全无关**；
* 它在库里留下的记录是 `status=BUILT`、`phase=READY`、`progress=100`，
  但 `expected_node_count=0 / ready_node_count=0 / failed_node_count=0`，
  且 `error_message` 为空——即**工件构建完成、分发/收尾没有推进**，
  客户端一直轮询到 480 s 超时；
* 部署的 TemplateCenter 二进制里确实存在 `BUILT` 这个中间态，以及
  `scan BUILT jobs` / `resume remote-built template job: start job_id=` 的
  reconciler 逻辑，说明这是"等待 reconciler 推进"的状态，只是没在 480 s 内推进；
* **单独重跑这一条：20.25 s 通过。**

也就是说：这是我用 `SDK_E2E_WORKERS=4` 在单节点上同时压 4 个沙箱+模板构建时，
平台模板流水线的收尾没有及时推进造成的，属于**我的测试配置**引入的干扰，
不是硬件/内核抖动，更与 envd 无关。

### 4.2 去掉并行变量后：288 用例逐一相同

两个模板都改成串行重跑：

```
stock: 271 passed, 16 skipped, 1 xfailed in 334.80s
pr27 : 271 passed, 16 skipped, 1 xfailed in 351.26s
```

逐 `testcase` 比对 JUnit：**288 个用例状态无一不同**（连"哪些用例 skip"都一致）。

## 5. 结果二：直连探针发现的真差异

探针脚本在服务器上直连 envd（经 CubeProxy，`sandbox.get_host(49983)`），
用与 SDK 相同的 access token / traffic token。

### 5.1 新能力：终止原因（本分支的 envd+SDK 配对改动）

上游 envd 的 `end` 事件只有 `signal`（proto 里连 `oomKilled`/`killedBy` 字段都没有），
cube-envd 读 cgroup 的 `memory.events` 扩展出这套上报。

`commands.run`：

| 场景 | stock（Go 0.5.11） | pr27（cube-envd） |
|---|---|---|
| `kill -9 $$` | `signal: null` | `signal: 9` |
| `kill -TERM $$` | `signal: null` | `signal: 15` |
| `kill -INT $$` | `signal: null` | `signal: null` |
| OOM | `oom_killed: false, killed_by: null` | `oom_killed: true, killed_by: "oom", signal: 9` |

PTY（`PtyHandle` 属性）：

| 场景 | stock | pr27 |
|---|---|---|
| pty 里 `kill -9 $$` | `signal: null` | `signal: 9` |

两点说明：

* `SIGINT` 两边都不上报——因为 proto 的 `Signal` 枚举只有 `SIGTERM=15` /
  `SIGKILL=9`，cube-envd 严格按枚举能表达的范围上报，没有自造字段。
* OOM 那条命令是一个无限分配循环，两侧都以 `exit_code: -1`（非正常退出）结束，
  差别只在**说不说得出原因**：我们给出 `oom` + signal 9，Go 侧什么也没有。
  其 stderr 还顺带暴露了架构差异：
  * stock：`/sys/fs/cgroup/default/<tpl>_0/user/memory.max`
  * pr27：`/sys/fs/cgroup/default/<tpl>_0/user/**process-2-10**/memory.max`
  即 cube-envd 给**每个命令**建独立 cgroup，Go envd 直接把命令放在 `user/` 下。
  这正是"能精确归因 OOM"和"能把 setsid 逃逸者一起收掉"的前提。

### 5.2 下载 gzip：机制不同，不只是参数不同

| 文件 | stock | pr27 |
|---|---|---|
| 8 MiB 文本，`Accept-Encoding: gzip` | 21,064 B，`Content-Type: application/octet-stream` | 49,023 B，`Content-Type: text/plain; charset=utf-8` |
| 64 MiB 二进制，`Accept-Encoding: gzip` | **260,655 B** | **67,108,864 B（未压缩）** |
| 16 B 小文本，`Accept-Encoding: gzip` | 40 B | 16 B（未压缩） |

机制（这次才查清）：

* Go envd **自己**压缩响应体，且**不看内容类型**，所以 `.bin` 也压；
  `Content-Type` 一律 `application/octet-stream`。
* cube-envd 不压缩；实际出现的 gzip 来自 **CubeProxy（nginx）**，而 nginx 只压
  `gzip_types` 里的类型、默认 `gzip_comp_level 1`。于是：
  * 文本：我们被压了，但压缩率差 ~2.3×（49 KB vs 21 KB）；
  * 二进制：不在 nginx 类型表里 → **整包 64 MiB 走线**（相差 257×）。

对用户的意义：只要下载内容是可压缩的非文本类型（或 nginx 类型表没覆盖的类型），
cube-envd 的流量会显著变大。这是目前最值得补的一项。

### 5.3 下载吞吐：2.9× 差距在真机上成立

64 MiB 文件、`Accept-Encoding: identity`、5 次取中位数（客户端按 chunk 累加并增量
哈希，避免之前那种把测量自身变成瓶颈的写法）：

| | 中位数 | 最好 |
|---|---|---|
| stock | **1374.9 MiB/s** | 1406.6 |
| pr27 | **475.2 MiB/s** | 540.3 |

8 MiB 文本同向（1088.5 vs 479.7 MiB/s）。两边 sha256 都校验通过。
这与本地推导一致（Go 走 `http.ServeContent` → `sendfile`，我们是分块读+写）。

### 5.4 其余逐项

| 探针 | stock | pr27 | 说明 |
|---|---|---|---|
| `HEAD /files` | 405 | 200 | 我们支持 HEAD，Go 不支持 |
| `POST /files/compose`（JSON 契约） | 200，写出目标文件、删除源文件 | 501 | 真实协议缺口；但两套 SDK 都不调用它，SDK 用户碰不到 |
| `Range: bytes=0-99` | 206，`bytes 0-99/7208960` | 相同 | |
| `Range: bytes=-100` | 206，`bytes 7208860-7208959/…` | 相同 | |
| 非法 Range | 416，`bytes */7208960` | 相同 | |
| 不存在文件 | 404 | 404 | 响应体 73 B vs 72 B（Go 的 JSON 末尾多一个换行） |
| 路径是目录 | 400 | 400 | 64 B vs 63 B，同上 |
| 假 `signature` | 200 | 200 | **两侧都忽略 signature** |
| 上传 64 MiB（octet-stream，5 次） | 752.1 MiB/s | 547.6 MiB/s | 我们慢 1.37× |
| 上传 64 MiB（multipart，5 次） | 475.9 MiB/s | 615.2 MiB/s | 我们快 1.29× |
| PTY 建立+销毁（15 次） | 中位数 4.6 ms | 中位数 3.0 ms | fork-free 的预期效果 |
| PTY 交互输出 | 42 B 首屏一致 | 42 B | |

## 6. 对之前几份本地结论的修正

| 之前写的 | 现在（真机） |
|---|---|
| 假 signature：Go 404 / 我们 200 | **撤回**。两侧都 200；之前那次 404 是因为探针在 compose 之后读了一个已被 Go 删除的源文件 |
| 我们不压缩下载 | 更准确：**我们不压，nginx 只对文本类型压且 level 1**；所以文本有压缩但更差，二进制完全不压 |
| 下载慢 2.2–5×（本地） | 真机 2.9×，成立 |
| 超时被杀的报错类型不同 | **撤回**。两次跑结果相反（一次 Go `deadline_exceeded` 我们 `ReadTimeout`，一次反过来），属于超时竞态，不是稳定差异 |
| PTY 首屏输出字节数差异 | **撤回**，是读取窗口的时序噪声，修正后两侧一致 |
| 上传被 `proxy_request_buffering` 掩盖 | 真机复现：两种模式的快慢方向相反，结论是"无稳定差异" |
